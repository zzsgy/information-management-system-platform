# 草稿盒整盒撤回与二次确认

2026-11-04 用户确认：删除草稿盒时一并撤回盒内草稿，保留历史记录与附件原件；已归档资料继续按原审批流程处理，并在删除提交前再次确认。

## 行为

- 点击提交删除草稿时，弹窗显示“再次确认删除草稿盒”、盒名、盒内草稿数量、已上传附件数量，以及历史和原件保留说明。确认与已有的本人身份核验合并在一个弹窗中，不再叠加第三次确认。取消不会提交写入。
- 盒内所有可直接撤回的草稿与盒在同一个事务中处理，各自记录前后状态、经办人、时间和原因。已撤回的旧条目保持原历史，不重复追加撤回记录。
- 盒或任一有效成员已归档、正在归档审批或原有受控流程未结束时，不通过草稿删除接口绕过原流程，也不会先撤回一部分草稿。
- 不删除、改写盒号、文件编号、不可变修订、原始附件、PDF 版本及存储引用。普通列表不再显示已撤回对象，获授权的历史查询继续保留。
- 沿用现有维护权限、原版本核对、幂等提交和审计；不增加新的批准节点或盒总容量上限。

## 同轮定位的通知查询瓶颈

原有目录变更通知查询会对每个账号执行 `archive.catalog_manager`，审批完成时曾触发十秒查询超时。现在先取得可能具有管理任职的候选人员，再由同一个正式授权函数决定最终接收人。没有提高超时，也没有缩减通知范围。

在独立测试库 55448、2,821 个有效合成账号下，按同一部门顺序测量：

| 查询 | 耗时（含数据库客户端连接） | 接收人 |
| --- | ---: | --- |
| 原实现 | 7,776.3 ms | 基准名单 |
| 优化实现 | 124.9 ms | 与基准完全一致 |

这是该查询在本机该合成数据集上的结果，不代表生产容量或整条审批链的性能验收。测量脚本直接读取正式 Java 实现中的 SQL；结果位于项目相邻 `tmp/draft_box_withdrawal_20261104/notification-query-measurement.json`。
