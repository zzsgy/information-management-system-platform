# 公盘与 Office 稳定性、并发验证（2026-10-30）

本批沿用电脑端 Vue 页面、Java 平台服务、独立 PostgreSQL 和本机 ONLYOFFICE，完成真实接口及浏览器的阶梯负载验证。测试只使用合成员工、文件和独立目录，不接入正式业务数据。

## 修复的问题

### 同一版本并发转换产生多余副本

两名调用者同时预览同一 Word 版本时，原实现会分别执行转换和双副本写入，最终数据库只引用一份结果，另一份留在磁盘。真实双线程用例先复现“应新增 1 个文件，实际新增 2 个”，随后验证修复。

`OfficeConversions` 按源版本、输出格式和转换器版本合并本进程正在执行的请求。同键请求共享结果，不重复占用两个转换工作位；跟随请求最多等候 5 秒、不持有数据库连接，超时返回既有 `OFFICE_CONVERSION_BUSY`，给普通接口和原生回调保留处理机会。结果交付前重新核验调用者权限及副本，失败后移除合并记录，允许后续重试。原件、扫描、双副本和不可变版本流程保持原有语义。

该合并作用于当前单活动应用进程，不构成跨节点分布式锁，也不证明多主写入已受支持。

### 临时断网被当作撤权而销毁编辑器

原页面把任何状态查询异常都当作撤权，真实浏览器断网后 iframe 数量变成 0。修复后，网络异常会隐藏编辑区、暂停保存及关闭按钮，并保留原生编辑器；网络恢复且平台重新鉴权通过后显示。同样的测试已验证 iframe 在失联时仍存在但不可见，接口恢复后同一个编辑器可继续使用。明确的鉴权失败仍执行原有清屏流程。

整个浏览器断网时，ONLYOFFICE 可能已提交最终保存并结束批次，此时平台按真实 `CLOSED` 状态结束，需要重新打开文件。本批核对了断网前已获同步确认的内容及最终文件；不承诺未送达文档服务的离线按键一定可恢复，也不支持离线编辑。

公盘通过正式 HTTPS 完成三路 16 MiB 文件并行上传，每个文件同时验证重复创建上传会话、重复分片和重复完成提交；发布后核对完整下载、8 MiB 断点续传及实际双副本摘要。三份文件从传片到核对完成分别约 4.7、5.8、11.9 秒。

独立子目录创建 1,000 条合成文件元数据，共享已检验的测试原件。查询始终经过真实权限过滤和分页，并非直接执行 SQL 计时。

环境为约 32 GiB Windows 宿主，ONLYOFFICE 限制 2 CPU、4 GiB 内存。本轮 20 人采样期间宿主最少可用内存约 3,601 MiB；容器没有 OOM 退出、重启次数为 0。20 人完成后仍通过 40 秒时钟连续性检查，回退 0 次，与宿主偏差约 0.081 秒。以上为本次观测值，不是资源峰值保证。

## 复跑入口

使用仓库现有 Maven、Playwright、Edge 和 Prettier，不新增压测工具。先构建 `web` 的 `build:platform`，再以 `-Pplatform` 构建 Java。Java 专项测试需读取本批私有环境配置，设置 `IMS_OFFICE_STABILITY_INTEGRATION=yes`、`IMS_DRIVE_TEST_ROOT`、`IMS_CLAM_TEST_EXE`、`IMS_OFFICE_TEST_SAMPLES` 和本机信任库；固定只允许本批 `55467 / 18467`，运行前停止该端口的测试应用。

启动测试应用后，浏览器阶梯验证示例：

```powershell
$env:IMS_OFFICE_TEST_FIXTURE = 'D:/tmp/ims-platform-stability-20261030/browser-fixture.private.json'
$env:IMS_OFFICE_TEST_URL = 'https://127.0.0.1:18467'
```
