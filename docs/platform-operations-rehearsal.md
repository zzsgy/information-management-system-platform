## 通知与投递

V20 新增 `ops.business_notification`、`ops.notification_delivery`、`ops.notification_attempt`；V21 将结果通知绑定不可变流程路线。已有迁移保留原文，变更另建迁移。

工作流当前节点、结果及改派，电子到期提醒、纸质交付后的提醒和归还事项，与原业务事务一起生成最小通知和独立投递任务。业务回滚时通知也回滚。审批人与原件权限仍由各自领域决定，消息只包含固定安全模板及受控引用。

读取和投递均重新核对当前来源：待办须仍为当前合法任职，结果须仍对应原路线及状态，电子提醒须仍对应有效截止，实物事项须仍属于本人或当前经办范围。补批产生新路线和新结果通知，初次批准的已读消息不能吞并补批结果，旧路线结果也不随同名 `APPROVED` 状态重新生效。

| 能力 | 行为 |
|---|---|
| 本人通知 | 授权后分页查询，已读保留首次时刻；跳转后由业务接口再次鉴权。 |
| 待办超期 | 当前合法节点超过原 24 小时办理时限后，按上海日期每日生成一次提醒。 |
| 稳定去重 | 业务事件、接收人和原任职/路线固定；一次通知对应一个稳定投递号。 |
| 并发领取 | 使用 `FOR UPDATE SKIP LOCKED` 和随机租约，默认单轮最多 20 项，最大 100 项。 |
| I/O边界 | 短事务领取，事务外投递，仍持有有效租约才确认结果；数据库连接不覆盖外部 I/O 等待。 |
| 自动重试 | 初次失败后再重试 3 次，默认间隔为 60、300、900 秒；耗尽后转人工。 |
| 中断恢复 | 租约到期保留 `UNKNOWN` 尝试，继续原投递号；连续 4 次中断也转人工。来源失效时停止过期任务。 |
| 人工重试 | 档案超级管理员填写修复原因，以原版本、操作号及精确本人再验证凭据重新排队。历史累计次数保留，消息任务不回调审批或借阅。 |
| 本批通道 | 私有本机投递箱，稳定文件名、独立刷盘和字节核对；重复发送核对同一文件，内容不符进入失败处理。正式适配器可实现 `BusinessMessageTransport`。 |

本批本机投递结果标注 `LOCAL_DEVELOPMENT_ONLY`。它证明本机适配器已持久化消息，不代表公司邮箱收到邮件。公司邮箱、钉钉等真实通道需在后续正式环境接入与验收。

### Service API

均沿用 `/api/v1`、HTTPS、有效会话和写请求 CSRF 检查：

| 方法与相对路径 | 输入、权限与失败语义 |
|---|---|
| GET `/portal/business-notifications` | 本人档案入口，`page/pageSize/unreadOnly`；单页最多 100，先筛选本人及有效来源再计数。 |
| POST `/portal/business-notifications/{id}/read` | 本人当前合法消息；重复确认保留首次时间，他人标识返回 404。 |
| GET `/admin/archive/notification-deliveries` | 档案超级管理员且有 `ARCHIVE.CONFIG_MANAGE`；按状态分页，返回最小收件人、次数、时间及脱敏错误。 |
| POST `/admin/archive/notification-deliveries/{id}/retry` | `reason` 必填；须 `X-Operation-Id`、`X-Expected-Version` 和绑定 `NOTIFICATION_DELIVERY/RETRY_NOTIFICATION` 的 `X-Reauth-Token`。仅有效来源的人工队列可重试；版本、状态或异体重放冲突返回 409。 |

## 维护工具

入口为 `scripts/platform/maintenance.cjs`，使用 Node.js 和受信 PostgreSQL 客户端。工具明确限定本机独立平台库，适合本批隔离演练。配置文件和输出目录均由当前维护账号私有保管；数据库口令通过进程环境交给 PostgreSQL 客户端。

```powershell
node scripts/platform/maintenance.cjs check --config D:/private/maintenance.private.json
node scripts/platform/maintenance.cjs backup --config D:/private/maintenance.private.json --output D:/private/new-backup
node scripts/platform/maintenance.cjs restore-verify --config D:/private/maintenance.private.json --bundle D:/private/new-backup --output D:/private/new-recovery --database ims_platform_test_restore_example --port 18451 --current-ledger D:/private/current-ledger
```

`check` 只读取配置、数据库版本、工具、持久目录、官方病毒库候选及保护事实签名/有效期。病毒库候选存在仍需真实检测；本机路径不同也不代表不同物理介质。报告明确保持生产高可用验收状态为未验证。

### 一致性和原件验证

备份前停止本批应用。工具持有全部平台表的 SHARE 锁，并将导出快照交给 `pg_dump`，直到表事实及持久文件复制核对完成。表按主键顺序流式计算每行规范表示的 SHA-256，避免全表聚合到单个内存对象。

两份 READY 文件对象另以数据库登记的长度与 SHA-256 独立核对，随后核对备份文件清单。检查失败时保留不完整演练证据；修复已核实的来源后，使用全新目录重试。正式备份清单仅在全套检查通过后生成。

恢复要求另一 PostgreSQL 实例、全新数据库及全新目录，先验证数据库包摘要、完整持久根集合及逐文件摘要，再恢复并核对全部表记录。当前安全账本须与平台实例及密钥代次配对，水位不低于备份；复制期间水位变化会停止验收。恢复应用默认关闭自动工作器并保持正文保护未配置，完成恢复协调后再决定开放入口。

表摘要比较发生在恢复应用启动前；之后的登录审计、会话和版本迁移会正常产生新记录。恢复工具保留原数据库、原附件和备份，已存在的目标拒绝覆盖。
